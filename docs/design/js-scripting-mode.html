A scripting mode over SQL — run JavaScript against a live connection

A new editor language where await db.query(...) and ordinary control flow work, so "for each row, run another query" is expressible without leaving the app. This is the design; no code has been merged beyond validation tests.

Author Olivier M. Esuka Date 2026-07-28 Status Proposal — pending review Scope apps/desktop

Why this exists

The problem, stated plainly

The query editor runs SQL only. Typed text goes straight to the driver — QueryTab.tsx attaches a LIMIT, then db-postgres/lib.rs:176 runs it as a single statement via sqlx::query().fetch(). There is no JavaScript runtime, no pool, no loop.

So the natural "MongoDB shell" instinct — pull rows, iterate, query again per row — has nowhere to run. Pasting that JS into the editor sends const users = … to Postgres, which rejects it as a syntax error. Today the honest answer is "use a JOIN", and it usually is the right one. But a genuine scripting surface unlocks the cases a JOIN can't express: per-row branching, calling a query whose shape depends on the previous result, staged migrations.

TL;DR. Add a per-tab Script language alongside SQL. Scripts run in an embedded rquickjs sandbox with a single injected capability — db.query() — that marshals back to the existing driver. The last query result fills the Data grid; console.log streams to the Message tab. Scripts can do anything a normal query tab can. No new process to ship.

Decisions locked

Three choices that shape everything

Sandbox engine

rquickjs

QuickJS embedded in Rust. ~1 MB, in-process, no sidecar to spawn, bundle, or code-sign. We hand it exactly one function and it can reach nothing else — no fs, no net.

Results model

Last query + log

The final db.query result populates the Data grid; console.log() streams to Message. Reuses the existing RowBatch contract almost unchanged.

Write policy

Same as SQL

Scripts can INSERT/UPDATE/DDL — whatever a normal tab can. No special restriction to build or explain; consistent with the editor users already know.

Availability

RDBMS only

Offered on SQL drivers (Postgres, MySQL) only — not Mongo or Redis. Mongo already has its own shell dialect; a JS-over-SQL tab has no meaning there. Gated on lang() == Sql.

Architecture

How a script executes, end to end

It mirrors the existing MongoDB path — the codebase's proven precedent for a non-SQL language over a driver: parse a string into commands, dispatch through the driver, stream RowBatches back over the same sink. The only new box is the sandbox.

The tab offers Script mode only when the active driver reports lang() == Sql (db-postgres/lib.rs:114). On a Mongo or Redis connection the toggle simply isn't shown — those drivers have their own languages, and db.query(sql) would be meaningless against them.

The injected capability

The sandbox never touches the DynConn. It gets one async host function. Each call resolves the connection out of AppState (state.rs:17) by the tab's connId and runs it through the same stream() the SQL path uses — so cancellation, pooling, and error handling all come for free.

// what the user writes in a Script tab
const users = await db.query("SELECT id FROM users WHERE active = true");

for (const u of users.rows) {
  const orders = await db.query(
    "SELECT * FROM orders WHERE user_id = $1", [u.id]);
  console.log(u.id, orders.rowCount);   // → Message tab
}

return users;   // last result → Data grid

Note this is still N+1 by construction — the sandbox is for cases a set operation genuinely can't express, not a license to loop where a JOIN would do. The docs should say so next to the feature.

Risks

What could bite us

  • Retired

    Async bridge: rquickjs promises ↔ Tokio. Cleared in P1. An Async-wrapped host function returns a Rust future exposed to JS as a Promise; AsyncContext::async_with + AsyncRuntime::idle drive it to settlement. A per-row query loop suspends and resumes correctly — proven by loops_and_queries_per_row.

  • Retired

    The QuickJS engine is !Send. Found & handled in P2. rquickjs's runtime/context can't cross threads, but Tauri commands require Send futures. Resolved by confining the engine to a dedicated OS thread with its own current-thread runtime + LocalSet, returning the outcome over a Send oneshot. All of this lives inside db_script::run, so callers just await a normal Send future.

  • Med

    Runaway scripts. An infinite loop or a query returning millions of rows can wedge a connection or exhaust memory. Mitigation: an interrupt handler with a wall-clock timeout, a cumulative row cap across all db.query calls, and reuse of the existing cancellation handle.

  • Med

    Result-set ambiguity. "Last query fills the grid" is simple but can surprise: a script whose last statement is a write returns no rows and shows an empty grid. Fix with a clear Message-tab summary ("ran 14 queries, 0 rows returned") so empty ≠ broken.

  • Low

    Param marshalling — deferred. The relational drivers still ignore bound params (stream takes an empty Params), so db.query(sql, params) accepts a params array but does not yet bind it — scripts interpolate values into SQL for now. Real binding lands in P5 alongside driver-side param support; the sandbox already parses the JS params to JSON, so only the driver half remains.

  • Low

    Dev-sidecar parity. Browser-mode dev runs against the Node dev-sidecar.ts, which has no rquickjs. Script mode either degrades gracefully there or the sidecar grows a matching JS path. Decide, don't discover.

Alternatives weighed

Why not the other paths

  • Deno/Node sidecar. Full modern JS, but ships a ~40 MB signed binary per platform and a process lifecycle to babysit — heavy for a query DSL. Reconsider only if scripts need npm.
  • boa (pure Rust). Cleanest build, no C deps, but slower and more spec gaps — more likely to trip on a user's script. rquickjs is the better fit today; boa stays the fallback if the C toolchain becomes a burden.
  • Views / CTEs. For the pipeline-shaped cases ("output of one feeds the next"), WITH chains already work with zero new code and belong in the docs as the first thing to try. Scripting is for what CTEs can't do.
  • PL/pgSQL DO blocks. Loops server-side, but returns no rows through our single-statement fetch() path and is Postgres-only. Not a general answer.
